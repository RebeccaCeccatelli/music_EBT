## Mode-marker bug (found and fixed)
- Investigated why Anticipation's training loss differs with/without the
  leading `AUTOREGRESS`/`ANTICIPATE` mode-marker token. Ran a controlled
  loss-comparison experiment using the model's own
  `forward_loss_wrapper(phase="valid")` on real validation data: 20/20
  samples showed lower loss WITH the marker (mean 0.9545 vs 1.0431, ~9%
  perplexity difference).
- Discovered `demo/app.py`'s own `_resolve_prompt()` was building
  Anticipation prompts WITHOUT this marker for named songs — fixed by
  prepending `AUTOREGRESS` in that code path.

## Why does Anticipation pretraining underperform REMI? (investigation started)
- Ruled out dataloader I/O-boundedness (confirmed healthy CPU pattern via
  live `ps` on compute nodes, unlike the earlier attribute-regressor
  training I/O bottleneck).
- Ruled out learning-rate miscalibration (`peak_learning_rate=0.0008`
  confirmed identical across REMI, Anticipation-original, and
  Anticipation-stabilized).
- Found gradient norms 2–2.65x higher for Anticipation than REMI.
- Narrowed to two hypotheses: effective batch size (64 vs REMI's 256) and
  MCMC step-size LR multiplier (2 vs REMI's 20).
- Designed and launched two **probe experiments** (Probe A: batch=256,
  Probe B: step-mult=20) resuming from a shared Anticipation-stabilized
  checkpoint, `--no_wandb`-isolated, 45-min time-limited.
- **Near-miss caught**: the first probe submission accidentally
  auto-resumed into the SAME wandb run as the live production job (via
  `train_model.py`'s checkpoint-based wandb-run-ID lookup). Caught within
  ~16 seconds before any data was logged, killed both probes, verified via
  wandb API that production run history was untouched, fixed by adding
  `--no_wandb` to both probe scripts, resubmitted successfully.
