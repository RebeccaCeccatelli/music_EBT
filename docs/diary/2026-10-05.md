## Plug-and-play guidance baselines for GPT-2 / Llama
- Motivation: every existing sweep compares guided EBT against *unguided*
  EBT, which shows EBT is controllable but not that it's *more*
  controllable than an AR model. Need guided-AR baselines under the same
  protocol (frozen model, no retraining).
- New `attribute_control/ar_guidance.py`, three methods:
  - **Expectation tilting** (REMI velocity/duration/pitch_register): at the
    same gated steps as EBT's guidance, exponentially reweights the
    attribute's own value tokens so the per-step expected value closes a
    fraction `strength` of the gap to the target. This is the min-KL
    change satisfying that moment constraint, and it keeps the total mass
    on those tokens fixed. It needs no regressor (only a token→value map),
    so it's a deliberately strong, attribute-specific baseline. EBT's
    regressor guidance is generic.
  - **Best-of-N**: one pool of max(N) unguided samples per prompt; keep the
    one closest to the target by the evaluation's own scorer, i.e. an
    oracle reranker.
  - **PPLM-style**: the existing Llama gradient branch in
    `call_model_forward_decode()`. It needs regressors trained on Llama's
    embeddings: `train_density.sh` already works with `CHECKPOINT=<llama
    ckpt>`, and now names the output dir `*_regressor_llama-remi_*`.
- `generate_remi()` takes an optional `hparams.logit_processor` (raw
  logits in/out, applied after the drum mask). It's the hook the tilt uses.
- `attribute_control/ar_guidance_sweep.py` + `job_scripts/mus/attr_control/
  ar_guidance_sweep.sh` follow the EBT sweep protocol: the same 16 prompt
  ids, ±0.5/1/2 corpus-stdev targets around a 3-draw per-prompt baseline,
  prompt 64 / gen 256, T=0.7, top-p 0.9, and the same bigram table. Output
  tables use the same `{columns, data}` layout as `sweep_tables/`.
- `attribute_control/aggregate_guidance_sweeps.py` scores EBT and AR
  tables with one piece of code (accuracy, MAE, bigram_ll, gvr).
- Verified: unit test of the tilt on synthetic logits (it hits the target
  mean to <2e-3, preserves attribute mass, respects the gate and the
  low-mass guard). A CPU smoke test on the real Llama ckpt moved velocity
  0.75 → 0.23 / 0.93 for targets 0.3 / 0.95. The full driver ran end to end
  on a stub dataset. Not yet run on GPU at full scale.

## Found: published directional accuracy over-counts "down" at low λ
- `aggregate_guidance_sweeps.py` reproduces `sweep_tables/aggregated.json`
  exactly for n / MAE / bigram_ll / gvr, but not accuracy. The cause is
  that the original aggregation counted `achieved == baseline` (guidance
  changed nothing) as a correct *down* push (`down = not up`). With strict
  comparison, "up" matches the reference exactly and "down" matches
  `achieved <= baseline`.
- Effect, REMI EBT (old ckpt job21290401): velocity λ=0.01 69.8% → 57.3%,
  λ=0.02 92.7% → 80.2%; duration λ=0.015 90.6% → 77.1%; pitch_register
  λ=0.01 64.6% → 53.1%. High-λ numbers are unaffected. The up/down
  "crossover" in `thesis_findings/2026-09-24_remi_guidance_strength_sweeps.md`
  is partly this artifact and needs re-checking with strict accuracy.

## Music-quality evaluation: MIDI-level metrics vs real data
- Problem (user): samples that score well on the current metrics often
  sound cacophonic or aimless. Why: `musicality_metrics.py` only has
  token-level signals. `ebt_energy` is the model judging itself (circular,
  and invalid across EBT vs baselines). `bigram_ll` checks local token
  grammar. `grammar_violation_rate` checks syntax. `repetition_ratio` was
  read as "lower is better", but real music repeats, so very low
  repetition is consistent with noise. None looks at key, consonance,
  rhythm or structure.
- New `eval/music_quality.py` (worktree `.claude/worktrees/music-quality`,
  branch `music-quality-eval`, commit 248600f). It works on decoded MIDI
  only, so it's tokenizer-agnostic. Metrics per piece: pitch-class
  entropy, scale consistency (best major/harmonic-minor fit), sharp
  dissonance (fraction of sounding pairs that are m2/M7/tritone), polyphony,
  pitch range, empty-beat rate, groove consistency (bar-to-bar onset
  Hamming), and bar self-similarity (best Jaccard match of a bar's
  (position, pitch class) set to an earlier bar). `compare` reports
  mean±std and the KDE overlapping area with real data (Yang & Lerch 2020)
  instead of higher-is-better.
- Sanity check on synthetic MIDI: a C-major chord+melody loop vs uniform
  random notes separate on every metric (scale 1.00 vs 0.62, dissonance
  0.05 vs 0.25, self-similarity 0.85 vs 0.12, groove 1.00 vs 0.63). OA is
  0.92 for same-distribution samples and 0.14 at a 3σ shift (theory ≈ 0.13).
- `eval/dump_reference_midi.py` + `job_scripts/mus/eval/music_quality_reference.sh`:
  decode 500 random real validation windows per tokenizer (256 tokens, the
  sweeps' generation length) and score them. Job 24936920 (CPU, mit_normal).
- Worktree setup for parallel sessions: created from local `main` (not
  origin, which lacks today's commits). The anticipation submodule is cloned
  from the local copy, and `data/mus/symbolic/datasets` + `logs/` are
  symlinked to the main checkout. The dataset symlink is added to
  `.git/info/exclude`.
- Reference sets done (job 24937256; first attempt 24936920 cancelled). The
  REMI decode initially failed on every window because `load_tokenizer()`
  with no config path silently builds a default REMI (vocab 284) instead
  of the dataset's `tokenizer.json` (vocab 427). Checked: the model
  checkpoints store the right path, so inference, the demo and the sweeps
  decode correctly. Only standalone `inference/mus/tokens_to_midi.py` (CLI)
  and the dump script were affected; the dump script is fixed.
- Scored 484/500 REMI and 425/500 Ant real windows. The rest have < 8
  pitched notes (drum-only or near-silent windows). Real-vs-real (REMI
  windows vs Ant windows, two independent real samples): mean OA 0.87,

  time in REMI). So ~0.87 is the practical ceiling for a generated set,
