  rounds today still didn't fix it: restructured `generate_all()` and
  `generate_solo_attribute_batch()`/added `generate_composed_multi()`'s
  compose path from single multi-yield generators into chained `.then()`
  steps (one small update per row/step instead of one huge combined
  update), on the theory that Gradio was dropping the tail of very large
  single updates — genuine improvement (audio stopped being silently

  + Network tabs, provided directly by the user) found the *actual* root
  cause: an uncaught `AbortError` thrown from Gradio's own `MinimalAudioPlayer.destroy()` —
  a real upstream Gradio bug in Audio-component teardown, fixed in
  [gradio-app/gradio#13808](https://github.com/gradio-app/gradio/pull/13808)
  (merged 2026-09-10, first released in Gradio 6.27.0). Installed Gradio was
  6.17.3, three months older.

  even import) — caught immediately, reverted before it could affect the
  shared `music_EBT` conda env any training job depends on. Chasing the
  compatible-version chain further showed *no* transformers 4.x version
  supports huggingface-hub≥1.0, and transformers 5.x (which does) requires
  torch≥2.5, one major version past the installed 2.4.0+cu121.

## New finding: real corpus attribute distributions
- User asked for the dataset's actual mean/velocity/duration/pitch-register
  values to judge what's out-of-distribution for guidance targets. Rather
  than answer from the existing mean/stdev-only `corpus_stats.json`, sampled
  2,000 fresh real training windows and computed true histograms — found
  duration is sharply right-skewed (a target like 0.69 has ~zero real
  density, explaining that variant's unusually long, unusual output) and
  pitch register's known up/down asymmetry is visibly a real skewed shape,
  not just a skewness-statistic abstraction. Published as an interactive
  artifact and written up properly in
  `docs/thesis_findings/2026-09-24_corpus_attribute_distributions.md` with
  static figures for citing directly.

## Found and fixed: Anticipation attribute-regressor training windowing bug
- While checking whether today's pitch_register regressor retrain (job
  23640180, `note_only_window`) actually fixed its known compressed-range
  problem, built a before/after eval script
  (`attribute_control/eval_pitch_register_regressor.py`) comparing true vs.
  predicted values on real held-out windows. Result was worse than before,
  not better — both true labels *and* predictions had collapsed toward
  ~0 for almost every sample.
- Root cause: `train_density_regressor.py`'s `DensityDataset` slices
  windows straight from `dataset.get_full_tokens(idx)` — the **raw**
  stored sequence (leading `AUTOREGRESS`/`ANTICIPATE` mode marker, and for
  the ~90% of data in `ANTICIPATE` mode, real event triplets interleaved
  with anticipated-control triplets) — with no call to `ops.split()` or
  mode-token stripping before treating every stride-3 index as a real
  (time, duration, note) triplet boundary. `generate_anticipation()`
  already does this cleanup before windowing at inference time; the
  training script never did. `note_only_window`'s stricter
  `raw_start -= raw_start % 3` alignment (relative to raw index 0, the mode
  token's position, not the true first-event position at index 1) made this
  *more* consistently wrong than the old unaligned windowing, which got
  lucky on roughly a third of windows by chance — explaining why the
  retrain looked worse, not better.
- Confirmed directly before touching training: a targeted before/after
  check on 300 real windows using `note_only_window`'s exact slicing showed
  only 2/300 (0.7%) yielding any valid pitch signal before the fix, vs.
  290/300 (97%) after, with the fixed mean landing right at the real corpus
  value (~0.44 vs. the known ~0.40–0.45).
- Confirmed this does **not** affect REMI regressors: REMI has no
  analogous mode-marker token, and its attribute functions
  (`compute_velocity`/`compute_duration_bias`/`compute_pitch_register`)
  scan for token IDs in a fixed range regardless of position, unlike
  Anticipation's fixed-stride extraction — nothing position-dependent to
  misalign.
- Fixed by calling the same `_anticipation_triplets()` cleanup
  `attributes.py` already uses for label computation once per
  `__getitem__`, before windowing, for any Anticipation tokenizer type.
  Resubmitted the pitch_register retrain with the fix (job 23658023,
  `mit_normal_gpu`) — not yet complete.
